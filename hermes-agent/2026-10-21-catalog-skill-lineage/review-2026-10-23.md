## What was asked

Blocking: the e-mail pattern at `textfeat.py:20` was quadratic on hostile input.
`anchor_strings` (`textfeat.py:80`) runs it on every tool result inside `post_tool_call`
(`hooks.py:150-152`, `:172`), results are capped at 2 MB rather than sanitised, and CPython's `re`
holds the GIL for the whole call, so Hermes' hook timeout cannot interrupt it. He timed the pattern
alone at about 2 s for 40 KB of `"a."`, 51 s for 200 KB, and over an hour for a 2 MB page, and
proposed the bounded form `(?<![\w.+-])[\w.+-]{1,64}@[\w-]+(?:\.[\w-]+)+\b`, plus a timing test
that feeds `anchor_strings` `"a." * 1_000_000` and one pathological input per pattern.

Recommended, not blocking: `skills.py:27-29` read `HERMES_HOME` from the environment, which is the
launch profile's home when one process serves several profiles, so writes in another profile's
session go unrecorded; `hermes_constants.get_hermes_home()` is profile-aware.

He closed with: "Push the fix, re-pin `sha:` here and comment when it's in; we'll review the delta
from `554a951a`." and "We'll add a disclosure line at merge."

## What changed

`531cdfc` — the e-mail pattern takes the proposed form. The local part is bounded to 64 octets
(RFC 5321) and anchored with a lookbehind instead of `\b`, so a run of word characters is no longer
re-scanned from every offset. `skills.py` takes the home from
`hermes_constants.get_hermes_home()` — imported inside the function so the value is resolved per
call — with an `HERMES_HOME` fallback for releases that predate the helper. `tests/test_textfeat_perf.py`
adds the reproducer and one hostile one-liner per pattern, each in its own process with a hard
timeout.

`466345a` — two corrections found while checking the first commit. The 2 MB guard's bar moved from
2 s to 5 s, because the bounded pattern alone runs 2 MB in 0.05 s but the whole `anchor_strings`
pass takes 0.6–1.2 s (seven other patterns scan the same text) and a slower runner could have
reached the old bar. And the changelog had described one behavioural difference where there are two;
the second is recorded in a test.

## Measurements

Same machine, CPython 3.11.16, one process per case, `findall` over `"a." * n`:

| Input | Old pattern | New pattern |
|---|---|---|
| 40 KB | 4.85 s | 0.0009 s |
| 200 KB | 149.87 s | 0.005 s |
| 2 MB | not run to completion (150 s at 200 KB puts it in hours) | 0.049 s |

Run-to-run variation on this machine was roughly 4–5 s at 40 KB and 104–150 s at 200 KB.

`anchor_strings` over `"a." * 1_000_000` (2 MB), the reproducer from the review: 0.66 s on an
idle machine and 1.2 s while a test suite was running in the background, of which the e-mail
pattern is 0.03–0.05 s and the rest is the other seven patterns. Per pattern on the same 2 MB,
worst to best: `_INSTALL` 0.212 s, `_PATH` 0.145 s, `_WORD` 0.142 s, `_URL` 0.074 s, `_IP` 0.067 s,
`_ENV` 0.067 s, `_COMMAND` 0.038 s, `_EMAIL` 0.027 s.

## Output differences

Twelve samples run through both patterns. Nine are identical, including
`bob.smith+x@example.co.uk`, `first.last@sub.domain.example.org`, `USER@EXAMPLE.COM`, `a@b.co`,
`123@456.789`, `名字@例子.中国`, a trailing-dot address, and `admin@localhost` (no match either way).
Three differ, in two classes:

1. A local part longer than 64 octets is no longer an anchor: `"y" * 65 + "@example.com"` and
   `"prefix." + "y" * 63 + "@example.com"` matched before and do not now. RFC 5321 caps the local
   part at 64 octets, and matching longer runs is what cost quadratic time.
2. An ASCII `-`, `+` or `.` immediately before an address is now the first character of the local
   part: `-name@example.com` filters to `-name@example.com` where it used to filter to
   `name@example.com`. RFC 5321 atext allows the character; the token is the same to a reader.

## The sibling plugins

Both were audited the same way — every module-level pattern timed on eleven 1 MB hostile inputs in
its own process, then the public entry points timed on seven 1 MB shapes.

`hermes-degeneracy-guard` — no super-linear pattern in the audit; the entry points on seven 1 MB
shapes were all under 0.3 s except `check_text` and `judge_tool_arg` on 150,000 numbered lines
(1.1 MB), at 2.19 s and 1.34 s, and doubling that input scaled linearly: 0.9 MB 0.84 s, 1.8 MB
2.33 s, 3.8 MB 4.60 s, 7.7 MB 9.13 s.
It does not read `HERMES_HOME` at all. No change, no release. (Its suite passes file by file on
this machine — 36 passed, 1 skipped across the five modules — but one combined run produces 36 setup
errors from the package-loading helper in `tests/_pkg.py` (`import_module('__init__')`); GitHub CI is
green at `ffc28d0`, and the audit above went through the public entry points directly.)

`hermes-provenance-gate` — two patterns in `claims.py` had the same shape as the one the review
found, two adjacent unbounded whitespace runs retried from every backtrack position. `_KEY_VALUE`
took 0.67 s on `"key"` + 1 MiB of spaces, and `_TRAILING_PAREN` did not finish in 30 s on `"a"` +
1 MiB of spaces + `"b"` because `sub()` retried its leading `\s*` at every offset. Both are rewritten
with possessive quantifiers and now take under 5 ms. Released as 0.1.1 with four regression cases in
`tests/test_performance.py`, each in its own process under a 20 s timeout. Not re-pinned here — the
catalog change waits for approval.

## Not fixed

The plugin repository's `hermes-tools` CI job is red on two end-to-end tests,
`test_foreground_verbatim_unrelated_and_user_rule[plain]` and `[stream]`
(`assert set() == {'indent'}`). It was red in the same two tests at `554a951a`, before any commit
here, and was green at `8df4bcb`; three commits sit between them — `eafe10f` (chain verification),
`6bd396e` (skill lookup by directory scan, and a change to how a user message quoting a page is
linked) and `554a951a` (README only) — so the regression narrowed to the first two, and is not part
of this review's request. Left alone rather than widened into this diff.

`hermes-provenance-gate`'s own full suite cannot be completed on this machine:
`tests/test_hermes_strings.py` does not finish within 150 s, with the fix applied and with it
stashed, so it is an environment problem rather than a regression here. Everything else passes —
733 passed, 2 skipped, 6 xfailed, corpora 213/213 with 0 blocked and 174/174 expected outcomes met —
and the four whitespace cases in `tests/test_performance.py` pass in 20 cases' worth of runs.
